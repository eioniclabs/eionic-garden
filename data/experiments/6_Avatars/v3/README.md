# EIONIC Garden — 6 Avatars, v3 (C++ Engine Port)

Experiment run produced by the **C++ port** of the EIONIC engine. Earlier experiments (v1, v2) were produced by the Python engine; v3 is the first run generated by the C++ port.

> **No narration in this run.** No conversation, inner-voice, or narrative logs are included. See [What is NOT included](#what-is-not-included-and-why).

## Run configuration

| Parameter | Value |
|---|---|

| Engine | C++ port, build v44 (the 44th internal porting iteration) |
| Mode | `--faithful` (all optional behaviour extensions disabled; follows the original Python engine's behaviour, with one exception: the micro-action tie-break rule, see [Determinism and verification](#determinism-and-verification)) |
| Avatars | 6 |

| Platform | Windows 11 / MSYS2 UCRT64, GCC 16.2.0 |

### About the simulation start date

Time-dependent conditions in the simulation are derived from the **simulated calendar date**, which advances 4 hours per tick from the start date above. It is not read from the wall clock during the run.

This differs from v1 and v2: the Python engine started those runs from the real date and time at which each run was launched, and did not use a fixed random seed. Time-dependent conditions in v3 therefore differ from v1/v2, and behaviour should not be compared tick-for-tick across them without accounting for this.

Raw per-tick hormone logs (`multi_avatar_hormones_log_*.txt`) and internal engine state (`memory/`, `dai/`, `world_snapshot.json`) are **not published**. They're the engine's working data, not analysis output, and are kept private; the workbook contains period-level summaries computed from the hormone logs. The decision log (PTF, described below) is recorded by the engine but is not published in v3. The engine source is not published either.

Timestamps inside the simulation data are **simulated** time. The only wall-clock values in the published files are the `Generated:` line in the `map_log.txt` header and the `Generated` cell on the workbook's `Metadata` sheet.

## Decision log (PTF): recorded, not published

The engine writes a decision log, `ptf_log.jsonl`, with one JSON row per avatar per tick, recorded **before** the avatar's action is finalized. It captures:

- `prob`: the probability the engine assigned to each of the 14 possible actions this tick
- `chosen`: the action that was actually sampled from that distribution
- `entropy`: Shannon entropy of `prob` (high = many actions were plausible; low = the choice was nearly certain)
- `was_forced`: whether the action was forced by a hard constraint rather than sampled

PTF is a passive record. It logs the decision, it never influences it. The workbook's action-diversity and entropy figures are not computed from PTF: they come from the realized actions and values in the per-tick hormone logs.

## God View (not included in this run)

God View is an **observer-only** analysis layer, separate from the simulation. It is designed to read only from snapshots that already exist and never to write to live avatar/world state. It was **not enabled** for this run. God View is specific to the C++ port (the Python engine has no counterpart), so it has no Python reference to be checked against; its own test is a self-consistency check, and parity between the C++ and Python engines has only been verified with it switched off.

What it computes, per avatar per tick:

- **Counterfactual best action**: for each of the 14 possible actions, an alignment score (the engine's own directive-alignment delta) is computed as if that action had been taken instead. The action with the highest score is logged as `optimal_action`; the gap between that and the score for the action actually taken is `alignment_gap`.
- **Expected value under the actual policy**: the probability-weighted average of that alignment score across all 14 actions (using the same distribution PTF logs), giving a 1-tick expected value.
- **Bounded-horizon policy search**: a short dynamic-programming search over the next *N* ticks (`--god-view-horizon`, default 3) to estimate how much better a short sequence of actions could have scored than the single best next action. This is a simplified projection (state held constant across the horizon, only tension propagated), not a full forward simulation.
- **Surprise (KL divergence)**: how far an avatar's realized action distribution, over a trailing window, has drifted from what the model expected.
- **Pairwise game-theoretic analysis**: when two avatars interact, their 14×14 action combinations form a payoff matrix (each avatar's alignment score plus a joint-interaction term). That interaction term is defined by the analysis layer itself; it is not a quantity measured from the engine. The analysis searches the matrix for pure-strategy **Nash equilibria** and reports whether the pair's actual actions happened to land on one.

"Optimal" here means optimal with respect to the engine's own alignment score, not a validated real-world policy. God View exists to answer *"how close to its own internal optimum did each avatar's behavior come, and was there a better joint outcome available?"*, a lens for judging decision quality, not a replacement for observing what actually happened.

## What is NOT included, and why

This run has **no `narrative_log.txt`, `conversation_log.txt` or `inner_log.txt`** (v2 includes them).

Those logs come from the optional Narrator layer, which uses an external LLM to write text. The Narrator is OFF in this run. It is excluded for two reasons:

1. **LLM output is non-deterministic.** The same simulation state can yield different text on each call.
2. **The Narrator feeds back into the simulation.** Narrated lines are stored in avatar memory and can resurface later; narrated social actions can trigger multi-turn conversation sessions that update social bonds; and, in the C++ engine, each line applies a small capped hormone nudge. The Narrator does not choose actions, but it changes the trajectory of a run, so a narrated run and an un-narrated run diverge from each other.

Keeping it off means everything published in v3 depends only on the engine, seed, and start date.

## Determinism and verification

With the narrator off, the C++ engine is deterministic: the same engine build, platform, seed, start date, flags, and tick count produce the same simulation output. This was checked on this experiment's configuration with two independent runs (same seed, same tick count): `map_log.txt` and the internal decision log (`ptf_log.jsonl`) were identical once the wall-clock `Generated:` / `generated` values were set aside. Because those two values change on every run, **raw file hashes differ between runs even though the simulation data is identical.**

Since the engine source is not published, outside readers cannot re-run the simulation. The published map log and workbook are analysis artifacts, not a reproduction kit.

**C++ vs Python.** The C++ port was compared against the Python engine (fixed seed and start date, narration disabled):

- Verified: a fixed seed (value not disclosed), `3500` ticks. All seven output categories matched (hormone log, world snapshot, map log, event log, decision log, memory, DAI). Text logs matched byte-for-byte apart from wall-clock timestamps; the decision log, memory and DAI files were compared as parsed JSON.
- Bit-exact agreement holds against CPython 3.12 or newer. With older Python versions, last-digit rounding differences can appear in displayed values.
- Any ticks beyond the verified length were produced by the C++ engine only.

**Micro-action tie-break.** The original Python engine picks the dominant micro-action of a tick with a method that breaks ties by string-set ordering, which varies from one Python process to the next. Earlier experiments (v1, v2) were also not seeded and started from the real date and time of each launch, so they were never reproducible. The C++ port replaces this tie-break with a fixed rule: a clear winner wins as before; on a tie the previous tick's dominant micro-action wins if it is among the tied ones, otherwise the one that appeared first. The comparison against Python above was made with the same rule applied to the Python side, and with a fixed seed injected into it. This is the one place `--faithful` deliberately differs from the original Python behaviour.

## Long-run stability (20,000 ticks)

To check whether the simulation stays healthy over a much longer horizon than the published 3,500 ticks, the same configuration was run for 20,000 ticks (6 avatars, 120,000 avatar-ticks, 40 windows of 500 ticks). The statistics were computed from the full per-tick hormone logs with `stability_report.py`; the numbers are in `stability.csv` and `stability_report.txt`. The first 3,500 ticks of the 20,000-tick run are identical to the published run (map logs compared, wall-clock header line excluded), so the first seven windows of the analysis describe the published run itself.

What the run shows:

- **Hormones stay in a narrow band.** Window means: cortisol 0.43–0.45, dopamine 0.66–0.67, serotonin 0.75–0.78, oxytocin 0.84–0.88, adrenaline 0.53–0.54, melatonin 0.63–0.64. Cortisol, dopamine and serotonin essentially never sit at their floor or ceiling (at most 0.2% of avatar-ticks in any window); oxytocin is near its ceiling in about 5% of avatar-ticks in every window.
- **No drift.** Comparing the first ten windows with the last ten, no hormone average moves by more than 0.006; the largest change in any tracked variable is in somatic load (−0.02).
- **Behavioural variety is constant.** Action entropy stays between 3.45 and 3.52 bits, and the spread of cortisol across avatars stays between 0.10 and 0.12, so the avatars remain different from one another.
- **Zones.** `nexus` holds about 88% of avatar-ticks (84–91% per window), `sanctuary` about 9%, `void` about 2%, `earth_zone` about 1%, and `chaos_field` under 0.1%, so it is almost unused.

In short, the run stays bounded and stationary: no collapse into a single zone, no hormone pinned at a limit, no loss of diversity. It also means the averages do not evolve over time; the system is homeostatic rather than developing.

Limits of this check: it is a single run with a single (undisclosed) seed; statistics are pooled over avatars; and the flag thresholds in the script are rules of thumb, not scientific constants.
