# Six Avatars — v4: lexicon narration

> v4 is the first release where narration comes from a **local lexicon**
> instead of an LLM. The engine already drives autonomous NPCs; the lexicon
> is the part still maturing.

## What this is

The six avatars in this folder are simulated agents driven by a hormone /
memory / relationship engine. They make their own decisions, remember events,
form relationships, and speak. In v1–v3, narration was generated by an
external language model. In v4, narration is generated **locally** by a
lexicon: a set of 455 clauses and 31 frames, compiled from 77 approved
senses, that turns the engine's per-tick intent into text.

No API calls. No model download. The lexicon runs as a Python process next
to the engine and writes three logs: narrative, conversation, inner monologue.

This folder publishes one baseline run (narrator off) and one narrated run
(narrator on with lexicon backend), both 20,000 ticks, corrected engine mode.

## Why a lexicon instead of an LLM

- **Offline.** No API key, no network, no cost per token.
- **Controllable.** The vocabulary and grammar are explicit files; we can
  read, edit and version them.
- **Extensible.** The long-term plan is a lexicon that updates itself from
  experience (context-aware → experience-updated → social transmission →
  invention). An LLM cannot be extended that way.
- **Reproducible (in principle).** Given the same intent and the same
  lexicon seed, the same text is produced. An LLM samples; the lexicon
  can be pinned.

The trade-off is quality. The lexicon composes from templates, so some
lines read mechanical or odd. Known issues are listed below.

The lexicon is still maturing, and its vocabulary is deliberately small
(77 approved senses) so every spoken word stays under explicit control.

## How narration reaches the avatars

The narrator produces text; the engine writes that text back into the avatar.
In the current engine this happens in four places:

1. **Memory echo** — a stored memory can resurface. The only write is a
   recall counter, which raises its chance of resurfacing again.
2. **Disclosure** — if an echo surfaces during a social action toward
   another avatar, the avatar may share it. A new memory (emotional value
   taken from the listener's state) and a relationship update are written.
3. **Narrated lines** — the line is stored in that tick's memory entry, in
   the relationship's recent thread, and as a received message in the
   target's memory.
4. **Conversation sessions** — short exchanges resolved within one tick;
   every turn updates both relationships and both memories, and gives the
   avatar(s) a small direct hormone nudge.

Only (4) writes hormones directly. The others write memory; memory-derived
quantities (somatic load, shadow intensity) are read by the hormone engine,
so memory writes can influence hormones indirectly.

**Consequence:** a narrated run is a *different* simulation from the baseline,
not the same simulation with text attached.

## The narrator is optional and non-blocking

The engine does not wait for the narrator process. It sends one request per
tick, applies whatever answers have arrived at the start of the tick, and
continues regardless. A late answer, or one superseded by a newer request,
is discarded.

This means:

- If the narrator is not connected, the engine still runs to completion and
  the narrated logs are simply empty.
- If the narrator is slow, some answers are discarded and the logs are sparse.
- A run started with the narrator option but without a connected client
  behaves like a no-narrator run.

The narrator runs as a separate process, so its effect on the simulation
depends on when each answer arrives relative to the tick. See
**Determinism** below.

## Baseline vs narrated: the simulation itself differs

The two published runs are not the same simulation with different logs.
Narration is written back into the avatars (memories and relationships,
plus a small direct hormone nudge during conversation sessions), and those
writes feed back into the simulation.

Measured on the two 20,000-tick runs:

| log | lines that differ | first difference |
|---|---|---|
| `map_log` | 119,626 of 160,010 (75%) | tick ~65: PurpleO chooses `Withdraw` in the baseline and `Observe` in the narrated run |
| `event_log` | 62,091 of 66,472 (94%) | tick ~24: `[NARRATOR:DISCARD]` appears only in the narrated run |
| `multi_avatar_hormones_log_*` | most lines differ | interleaved narrator lines shift line positions; underlying hormone values also differ |

The divergence is not a floating-point rounding: an avatar takes a different
action, in a different zone, at a different target. After tick ~65 the two
runs are genuinely different trajectories.

The first difference at tick ~24 is a narrator bookkeeping line
(`[NARRATOR:DISCARD]`), not an action. The first **action** difference is at
tick ~65. Which of the four write paths above triggers the first action
difference has not been isolated.

## Known limitations (lexicon)

- **Body-part-as-agent.** Template composition lets physical parts take
  mental or social verbs: *"My eyes think"*, *"My voice confronts X"*.
- **Duplicate target.** *"I speak to X and I watch X"* — the target is
  named twice in one line. Frequent in conversation.
- **Unnatural negations.** *"My breath is not sharp"* — the adjective pool
  is not gated per body part.
- **Event voicing is low.** Traumatic or intimate events (TRAUMA, INTIMACY,
  …) are rarely voiced, even when present in the intent.
- **Far / near / self-directed wording never fires.** The engine does not
  yet pass `target_distance` / `self_directed` to the narrator.
- **Epoch gating is inactive.** `epoch_view` is not passed from the live
  registry, so epoch-specific vocabulary is not filtered in.

These are tracked as TODO for the next iteration.

## Engine notes

- The engine is a C++ port of the original Python implementation. From v4
  it uses the **corrected mode** by default: three quirks of the original
  (social-bond valence always 0.0, empty nearby-avatar list in memory,
  empty snapshot fields) are fixed. The startup banner reports the mode as
  `valence_fix=1 nearby_fix=1 snapshot_real=1`.
- The original behaviour is kept behind `--faithful` for regression checks
  and to reproduce v1–v3.
- **v1–v3 were produced with the original behaviour**, so they are not
  directly comparable with v4 runs.
- Feature flags in `engine/p6_engine_db.yaml` (MOVEMENT_RESONANCE,
  SPATIAL_COMMITMENT, ACTIVITY_COMMITMENT) are `False` for both runs in
  this folder.

## Determinism

The engine is deterministic with the narrator off: two runs with the same
build and seed produce bit-identical output. Verified with 10k-tick and
20k-tick runs; verification logs are internal records and are not included
here.

Narrated runs are **not** bit-reproducible. Even with the narrator connected
from tick 1, the timing of each response relative to the engine's tick
determines whether it is applied or discarded. Two narrated runs can
therefore drift apart, and the drift point is not predictable. This is
inherent to the asynchronous design, not a bug in the lexicon.

The narrated run in this folder is one such run, not a canonical one.

## Not published

Per-tick probability tables (`ptf_log.jsonl`), memory state, DAI state and
raw hormone logs are not published. They expose internal model state in a
form that can be used to reconstruct it. The workbooks above contain
aggregates, not per-tick values.

## Limits

- One seed, one machine, one build. A different build can shift the last
  digits of floating-point values.
- The lexicon is under active development; the published narrated run is a
  single snapshot, not a representative sample.
- The divergence between baseline and narrated (Section *Baseline vs
  narrated*) has not been causally isolated: it reflects narration write-back,
  but the exact contribution of each of the four write paths (echo,
  disclosure, narrated lines, conversation sessions) is not measured here.
- "Deterministic" refers to file-level comparison with wall-clock stamps
  ignored.

## Status

The simulation engine already drives autonomous NPCs: they decide, remember,
form relationships, and speak through a local lexicon. The gap to a shippable
product is presentation (visuals) and a simple rule layer, not the autonomy.
The lexicon is still maturing, and its vocabulary is deliberately small
(77 approved senses) so every spoken word stays under explicit control.
